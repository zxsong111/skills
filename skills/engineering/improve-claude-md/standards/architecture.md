# Directory structure and layering

**Applies when:** Projects with two or more modules / layers

**Probe first:** Top-level structure from `git ls-files`; import relationships (who imports whom); generated code directories (`gen/`, `__generated__`, `*.pb.go`)

## Items to decide

Decide each item; write "not applicable" for any this project doesn't need. Phrase each one as a checkable sentence.

| Item | What to decide | Example |
|---|---|---|
| Directory responsibilities | One sentence per top-level directory on what goes in it | `src/domain/` is pure business logic with no framework dependency |
| Dependency direction | Spell out who must not import whom | `domain` must not import `api` or `db` |
| Entry points | Where the program entry, route registration, and DI wiring live | `src/main.py` |
| Generated code | Which directories are generated; never hand-edit them, change the source and regenerate | `src/gen/**` is generated by `make proto` |
| Where new modules go | The default home for new features | One `src/<domain>/` per business domain |

## Where it lands

- Layer 2: where tooling can enforce dependency direction, use it (eslint `no-restricted-imports`, import-linter, ArchUnit)
- Layer 1: generated code directories go in `permissions.deny` as `Edit(<dir>/**)` (a `Write(...)` rule is accepted but has no effect)
- Layer 5: the directory responsibility overview goes in CLAUDE.md "Project structure", covering only what the directory names don't reveal
