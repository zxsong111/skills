# UI 原型（UI Prototype）

在同一个路由上生成**几个截然不同的 UI 变体**，通过一个悬浮底栏切换。用户在浏览器里来回翻看各个变体，选中一个（或者从每个里各偷一点），然后把其余的扔掉。

如果问题关乎逻辑/状态，而不是某个东西长什么样，那就走错分支了。请用 [LOGIC.md](LOGIC.md)。

## 什么时候适合这种形态

- 「这个页面应该长什么样？」
- 「我想在定下来之前先看看这个仪表盘的几种方案。」
- 「给设置页试一种不同的布局。」
- 任何用户否则会花一整天在脑子里纠结三个模糊草图的时候。

## 两种子形态：强烈优先选子形态 A

UI 原型**和应用的其余部分挨在一起**时要好判断得多：真实的页头、真实的侧边栏、真实的数据、真实的信息密度。一个孤零零的一次性路由就是真空：每个变体单独看都还行。只要有一个说得过去的现有页面可以承载变体，就默认选子形态 A。只有当原型确实在附近找不到落脚处时，才动用子形态 B。

### 子形态 A：调整现有页面（首选）

路由已经存在。变体渲染在**同一个路由上**，由 URL 查询参数 `?variant=` 控制。现有的数据获取、参数和鉴权全部保留。只替换渲染部分。这是默认选项；除非有特定理由，否则就选它。

如果要做原型的东西还没有自己的页面，但*自然会放在某个页面里*（仪表盘的一个新区块、设置页上的一张新卡片、现有流程中的一个新步骤），它仍然属于子形态 A。把变体挂载在宿主页面里。

### 子形态 B：新页面（最后手段）

只有当要做原型的东西确实没有可以容身的现有页面时才用它（例如一个全新的顶层界面，或者一个没法合理嵌入任何地方的流程）。

按项目已有的路由约定创建一个**一次性路由**。不要自创新的顶层结构。命名要一眼看出是原型（例如在路径或文件名里包含 `prototype` 这个词）。同样使用 `?variant=` 模式。

在决定用子形态 B 之前，先自查一下：真的没有任何现有页面可以嵌入吗？空路由会掩盖那些在填满内容的页面上会暴露出来的设计问题。

两种子形态的悬浮底栏完全相同。

## 流程

### 1. 说清问题并选定 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而是开始变成噪音，所以上限是 5。

用一行写下计划，放在原型所在位置或文件顶部的注释里：

> 「设置页的三个变体，通过 `?variant=` 切换，放在现有的 `/settings` 路由上。」

无论用户在不在场反驳，这一步都管用。

### 2. 生成截然不同的变体

为每个变体起草。每个都要符合：

- 页面的用途以及它能拿到的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，不管是什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：不同的布局、不同的信息层级、不同的主要交互入口，而不只是颜色不同。三个稍微改了改的卡片网格不叫 UI 原型，那叫壁纸。如果有两个草稿出来太像，就带着明确的「不要用卡片网格」指示重做其中一个。

### 3. 把它们接起来

在路由上创建一个切换组件：

```tsx
// 伪代码，按项目所用框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：所有现有的数据获取都保留在切换组件之上；每个变体只改变渲染出来的子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换组件。

### 4. 构建悬浮切换器

一个固定定位在屏幕底部居中的小栏，包含三部分：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前变体的键，如果变体导出了名字，也一并显示。例如 `B (Sidebar layout)`。
- **右箭头**：向后切换（循环）。

行为：

- 点击箭头会更新 URL 查询参数（使用框架自带的路由，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体可以分享，刷新后也保持不变。
- 键盘：`←` 和 `→` 方向键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 处于焦点时，不要拦截方向键。
- 视觉上和页面区分开（例如高对比度的胶囊形状、淡淡的阴影），让人一眼看出它不属于正在评估的设计。
- 在生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价的检查做门控，这样即使原型被误 merge，也不会把这个栏发给用户。

把切换器放在一个共享组件里，让两种子形态都能复用。放在项目里存放共享 UI 的地方。

### 5. 交付

给出 URL（以及各个 `?variant=` 的键）。用户有空时会翻一遍。有意思的反馈通常是**「我想要 B 的页头配 C 的侧边栏」**，这才是他们真正想要的设计。

### 6. 留存答案并清理

某个变体胜出之后，先留存答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 描述的方式留存原型。把胜出者合入真实代码，其余的移到一次性 branch 上，而不是留在 main 里：

- **子形态 A**：把胜出者合入现有页面；从 main 中删掉落选的变体和切换器。
- **子形态 B**：把胜出的变体升级为真正的路由；从 main 中删掉一次性路由和切换器。

全部变体合起来是一手资料（primary source），所以它们去一次性 branch，而不是进垃圾桶，因为留在 main branch 里的变体组件和切换器很快就会腐烂，还会让下一个读代码的人困惑。

## 反模式

- **变体只在颜色或文案上不同。** 那是微调，不是原型。真正的变体在结构上各执己见。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就失去了意义。每个变体都应该可以自由地推翻布局。
- **把变体接到真实的写操作上。** 只读原型没问题。如果某个变体需要写数据，就让它指向一个桩：问题是「这个应该长什么样」，而不是「后端能不能用」。
- **把原型直接升级到生产环境。** 变体代码是在原型约束下写的（没有测试，错误处理极少）。合入时要好好重写。
