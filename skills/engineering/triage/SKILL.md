# Triage

让项目 issue tracker 上的 issue 在一个由分诊角色(triage role)构成的小型状态机中流转。

如果这个 repo 把外部 pull request 当作请求入口（见 issue tracker 配置），分诊(triage)也覆盖它们：**PR 就是附带了代码的 issue**，使用相同的角色、相同的状态、相同的状态机，只有少数差异在下文标为「对于 PR」。按 tracker 配置把一个光秃秃的 `#42` 解析为 issue 或 PR。

分诊期间发到 issue tracker 上的每一条评论或 issue **都必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何写出经得起时间考验的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：已完全明确，可以交给 AFK agent
- `ready-for-human`：需要人来实现
- `wontfix`：不会处理

对于 PR，同样的状态是对照所附代码来解读的：`ready-for-agent` 表示已附上简报，应由 agent 在这个 diff 上推进下一步；`ready-for-human` 表示它已经可以由人来 merge。

每个已分诊的 issue 都应该恰好带一个类别角色和一个状态角色。如果状态角色互相冲突，先指出来并询问维护者，再做其他任何事。

这些是规范的角色名。issue tracker 里实际使用的标签字符串可能不同。这个映射应该已经提供给你了。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

状态流转：一个没有标签的 issue 通常先进入 `needs-triage`；从那里再转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者随时可以推翻；看起来不寻常的流转要指出来，先问再继续。

## 调用方式

维护者调用 `/triage`，用自然语言描述想做什么。理解请求并执行。例如：

- 「给我看看所有需要我关注的东西」
- 「我们来看看 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有哪些可以交给 agent 领取的？」

## 展示需要关注的内容

查询 issue tracker，分三个桶展示，最旧的在前：

1. **无标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **自上次分诊记录以来报告者有新动态的 `needs-info`**：需要重新评估。

当 PR 也在范围内时，把外部 PR 也纳入这些桶，并给每一行标上 `[PR]` 或 `[issue]`。发现阶段只列出*外部* PR（tracker 配置定义了谁算外部），所以协作者正在进行中的 PR 不属于分诊工作。这个过滤只作用于发现阶段；被明确点名的 PR 不论作者是谁都要分诊。

显示数量，每项附一行摘要。让维护者挑选。

## 分诊某个具体的 issue 或 PR

1. **收集上下文。** 完整阅读这个 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还有 diff）。解析之前的所有分诊记录，避免重复询问已解决的问题。用项目的领域术语表(glossary)探索代码库，尊重该区域的 ADR。对照代码库做两项检查：(a) **冗余**：按领域概念（而不只是请求的字面措辞）搜索所请求行为是否已有实现，并报告你查了哪些地方。如果找到了，它就是一个「已实现」的 `wontfix`（第 5 步）。(b) **先前拒绝**：阅读 `.out-of-scope/*.md`，把与这个请求相似的条目找出来。

2. **给出建议。** 告诉维护者你建议的类别和状态及理由，再附一段与该请求相关的代码库简要总结（包括它是否已经实现）。等待指示。

3. **验证说法。** 在任何盘问(grilling)之前，先确认这个说法站得住。对于 bug，按报告者给的步骤复现。对于 PR，确认 diff 做到了它声称的事：把它 checkout 下来，运行相关的测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（这是一个强烈的 `needs-info` 信号）。经过确认的验证会让 agent 简报有力得多。

4. **盘问（如有需要）。** 如果请求需要补充细节，调用 Skill 工具两次，参数分别为 "grilling" 和 "domain-modeling"，每次一轮问题地把它盘问成形，随着决策落地，就地打磨领域术语并更新 `GLOSSARY.md`/ADR。

5. **落实结果：**
   - `ready-for-agent`：发一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但要注明它为什么不能委派（判断性的决定、外部访问权限、设计决策、手动测试）。
   - `needs-info`：发布分诊记录（模板见下）。
   - 对于 `wontfix`，关闭 issue，评论内容取决于*原因*：
     - **已实现**：这个改动在代码库里已经存在。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库是给*被拒绝*的请求用的，不是给已建成的）。
     - **拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：打上这个角色。如果有部分进展，可以选择性地评论。

## 快速覆盖状态

如果维护者说「把 #42 移到 ready-for-agent」，信任他，直接打上这个角色。先确认你要做的事（角色变更、评论、关闭），然后执行。跳过盘问。如果在没有盘问会话的情况下移到 `ready-for-agent`，问他们是否要写一份 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- 要点 1
- 要点 2

**What we still need from you (@reporter):**

- 问题 1
- 问题 2
```

把盘问期间解决的所有事项都记在 "established so far" 下面，这样工作成果不会丢失。问题必须具体、可操作，而不是「请提供更多信息」。

## 恢复之前的会话

如果 issue 或 PR 上已有之前的分诊记录，先读它们，检查报告者是否回答了任何悬而未决的问题，在继续之前先给出更新后的全貌。不要重复询问已解决的问题。
