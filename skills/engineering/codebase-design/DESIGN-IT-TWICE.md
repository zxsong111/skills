# 设计两次（Design It Twice）

当用户想为选定的加深候选探索备选接口时，使用这种并行子 agent 模式。它基于 Ousterhout 的「设计两次」（Design It Twice）：你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇：**模块**（module）、**接口**（interface）、**接缝**（seam）、**适配器**（adapter）、**杠杆**（leverage）。

## 流程

### 1. 框定问题空间

在启动子 agent 之前，先为选定的候选写一段面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它会依赖哪些东西，以及这些依赖属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示意代码草图，用来让约束落地；它不是提案，只是让约束变得具体的一种方式

把这些展示给用户，然后立刻进入第 2 步。子 agent 并行工作的同时，用户在阅读和思考。

### 2. 启动子 agent

并行启动 3 个以上的子 agent。每个都必须为加深后的模块产出一个**截然不同**的接口。

给每个子 agent 一份独立的技术简报作为 prompt（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后放什么）。这份简报独立于第 1 步中面向用户的问题空间说明。给每个 agent 一个不同的设计约束：

- Agent 1：「把接口压到最小：入口点最多 1 到 3 个。让每个入口点的杠杆最大化。」
- Agent 2：「把灵活性做到最大：支持多种用例和扩展。」
- Agent 3：「为最常见的调用方优化：让默认情况变得轻而易举。」
- Agent 4（如适用）：「围绕端口与适配器（ports & adapters）来设计跨接缝的依赖。」

在简报中同时放入 [SKILL.md](SKILL.md) 的词汇和 GLOSSARY.md 的词汇，让每个子 agent 的命名都与架构语言和项目的领域语言保持一致。

每个子 agent 输出：

1. 接口（类型、方法、参数，以及不变量、顺序、错误模式）
2. 展示调用方如何使用它的用法示例
3. 实现在接缝背后隐藏了什么
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡：哪里杠杆高，哪里杠杆薄

### 3. 展示并比较

逐个展示设计，让用户能消化每一个，然后用文字比较它们。从**深度**（接口处的杠杆）、**局部性**（变更集中在哪里）和**接缝位置**三方面进行对比。

比较之后，给出你自己的推荐：你认为哪个设计最强，为什么。如果不同设计中的元素组合起来效果更好，就提出一个混合方案。要有主见：用户想要的是一个明确的判断，而不是一份菜单。
