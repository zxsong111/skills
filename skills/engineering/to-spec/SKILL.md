这个 skill 利用当前对话的上下文和对代码库的理解，产出一份 spec。**不要**盘问用户；只综合你已经知道的内容。

issue tracker 和分诊(triage)标签词汇表应该已经提供给你了。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果还没探索过，先探索 repo，了解代码库的现状。整份 spec 都使用项目领域术语表(glossary)中的词汇，并尊重你所触及区域的所有 ADR。

2. 勾勒出你准备在哪些接缝(seam)处测试这个功能。优先用现有接缝，而不是新建。尽量用最高层的接缝。如果需要新接缝，就在你能做到的最高位置提出。整个代码库中的接缝越少越好，理想数量是一个。

和用户确认这些接缝符合他们的预期。

3. 按下面的模板写 spec，然后发布到项目的 issue tracker。打上 `ready-for-agent` 分诊标签，不需要再做额外的分诊。

<spec-template>

## 问题陈述

用户面临的问题，从用户的视角描述。

## 解决方案

问题的解决方案，从用户的视角描述。

## 用户故事

一份很长的、带编号的用户故事列表。每个用户故事都采用如下格式：

1. 作为一个 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为一个手机银行用户，我想看到我各个账户的余额，以便对自己的支出做出更明智的决定
</user-story-example>

这份用户故事列表应该极其详尽，覆盖这个功能的方方面面。

## 实现决策

已经做出的实现决策列表。可以包括：

- 将要新建或修改的模块
- 将要修改的那些模块的接口
- 开发者给出的技术澄清
- 架构决策
- schema 变更
- API 契约
- 具体的交互

**不要**写具体的文件路径或代码片段。它们可能很快就会过时。

例外：如果某个原型产出了一段代码，它表达一个决策比文字更精确（状态机、reducer、schema、类型结构），就把它内联到相关决策里，并简短注明它来自原型。只保留富含决策的部分，不是一个能跑的 demo，只要关键的几处。

## 测试决策

已经做出的测试决策列表。包括：

- 什么样的测试是好测试（只测外部行为，不测实现细节）
- 哪些模块会被测试
- 测试的先例（即代码库中类似类型的测试）

## 范围之外

对本 spec 范围之外事项的描述。

## 补充说明

关于这个功能的任何补充说明。

</spec-template>
